## วัตถุประสงค์การเรียนรู้

เมื่อจบสัปดาห์นี้ ผู้เรียนสามารถ

1. สาธิตระบบสำรวจข้อมูลของตนเองตั้งแต่แหล่งข้อมูลจนถึงแดชบอร์ดได้แบบ end-to-end
2. นำเสนอคำตอบของคำถามเชิงวิเคราะห์พร้อมหลักฐานและระดับความมั่นใจ
3. อธิบายข้อจำกัดของข้อมูลและวิธีการ ประเด็นจริยธรรม/PDPA และการใช้ AI อย่างตรงไปตรงมา
4. ตอบคำถามเชิงเทคนิคเกี่ยวกับโค้ดของตนเองได้ทุกส่วน
5. ประเมินงานของเพื่อนอย่างสร้างสรรค์และสะท้อนการเรียนรู้ของตนเอง

## 1. ภาพรวมการประเมิน

สัปดาห์นี้ไม่มีเนื้อหาใหม่ เป็นการรวบรวมผลงาน 14 สัปดาห์ให้เป็นระบบเดียวที่ **คนอื่นรันได้** และ **ตอบคำถามที่ตั้งไว้ในสัปดาห์ที่ 2** ได้

```text
แหล่งข้อมูล (API / เว็บ) → DuckDB → pandas → Plotly → Streamlit dashboard
      สัปดาห์ 3              4         5–7      9–13         14
                 + คำถาม (2) + คุณภาพข้อมูล (6–7) + PDPA (12) + รายงาน (14)
```

| องค์ประกอบ | สัดส่วน | ประเมินจาก |

## 2. สิ่งที่ต้องนำเสนอ

| ส่วน | สิ่งที่ต้องแสดง | CLO |
|---|---|---|
| 1. โจทย์และคำถาม | ปัญหาคืออะไร ใครได้ประโยชน์ คำถามจาก `questions.md` 3–4 ข้อ (ระบุถ้าคำถามเปลี่ยนไประหว่างภาค และเพราะอะไร) | CLO4 |
| 2. Demo ระบบ end-to-end | รัน (หรือแสดง log การรันล่าสุดของ) `python run_all.py` → แสดงตารางใน DuckDB → เปิดแดชบอร์ดและ drill-down ประเทศ → ภาค → จังหวัด → สถานี | CLO1, CLO2, CLO5 |
| 3. คุณภาพข้อมูล | ปัญหาที่พบ (ค่าหาย, outlier, พิกัด/ชื่อจังหวัดผิด) และการตัดสินใจพร้อมเหตุผล | CLO3 |
| 4. คำตอบของคำถาม | ข้อค้นพบหลักต่อคำถาม หลักฐานจากกราฟและสถิติ และระดับความมั่นใจ (ใช้รายงาน Quarto หรือแดชบอร์ด) | CLO4, CLO5 |
| 5. ข้อจำกัด | ข้อจำกัดของข้อมูล (สถานีกระจุกในเมือง, ช่วงเวลา, MAUP) และวิธีการ (ความสัมพันธ์ ≠ เหตุและผล, cluster เป็นสมมติฐาน) | CLO4, CLO6 |
| 6. จริยธรรมและ PDPA | ข้อมูลที่ใช้เป็น/ไม่เป็นข้อมูลส่วนบุคคล ความเสี่ยงถ้าต่อยอดกับข้อมูลสุขภาพ การใช้ข้อมูลสังเคราะห์ สัญญาอนุญาตของแหล่งข้อมูล | CLO6 |
| 7. สะท้อนการใช้ AI | AI ช่วยส่วนใด ตัวอย่างที่ AI ผิด (เช่น ชื่อคอลัมน์/endpoint ที่ไม่มีจริง) และตรวจพบอย่างไร สิ่งที่เรียนรู้ | CLO6 |

**หลักการนำเสนอ:** เริ่มด้วยข้อค้นพบที่สำคัญที่สุด 1 ข้อ แล้วค่อยแสดงว่าระบบหาคำตอบนั้นได้อย่างไร ไม่ต้องเล่าทุกสัปดาห์ตามลำดับเวลา

## 3. ลำดับและเวลา

ผู้นำเสนอแต่ละคนมี **15 นาที** (นำเสนอ 10 นาที + ถามตอบ 5 นาที) ผู้สอนจะหยุดเมื่อครบเวลา

| นาที | ส่วน |
|---|---|
| 0–1 | โจทย์ คำถาม และข้อค้นพบหลัก 1 ประโยค |
| 1–5 | Demo ระบบ end-to-end + drill-down บนแดชบอร์ดสด |
| 5–8 | คำตอบของคำถาม + คุณภาพข้อมูลที่กระทบคำตอบ |
| 8–10 | ข้อจำกัด, PDPA/จริยธรรม, สะท้อนการใช้ AI |
| 10–15 | ถามตอบ (ผู้สอนและเพื่อน) |

ข้อแนะนำด้านเทคนิค

- ใช้ฐานข้อมูลที่สร้างไว้ล่วงหน้า การดึงข้อมูลสดอาจช้าหรือ API ล่มระหว่างนำเสนอ ให้แสดง log การรัน `run_all.py` ครั้งล่าสุดแทนได้
- เปิดแดชบอร์ด รายงาน HTML และ GitHub repo ไว้ล่วงหน้าคนละแท็บ
- เตรียมภาพหน้าจอสำรอง (backup) ในกรณีเครื่องหรือเครือข่ายมีปัญหา แต่การ demo สดได้คะแนนเต็มกว่า
- สไลด์ไม่บังคับ ถ้าใช้ไม่ควรเกิน 6–8 หน้า หรือใช้รายงาน Quarto เป็นสื่อนำเสนอได้

## 4. ตัวอย่างคำถามในช่วงถามตอบ

ผู้สอนจะเลือกโค้ด *ส่วนใดก็ได้* ใน repo ให้อธิบาย ตามนโยบาย AI ของรายวิชา ถ้าอธิบายไม่ได้ถือว่าส่วนนั้นไม่ใช่ผลงานของตนเอง

| หมวด | ตัวอย่างคำถาม |
|---|---|
| Pipeline | ถ้า Air4Thai เปลี่ยนชื่อ field ใน JSON ระบบจะพังที่ไหน และรู้ได้อย่างไร |
| DuckDB | `daily_pm25_clean` คำนวณอย่างไร วันที่มีข้อมูลไม่ครบ 24 ชั่วโมงจัดการอย่างไร |
| คุณภาพข้อมูล | เลือกวิธีจัดการค่าหายนี้เพราะเชื่อว่ากลไกเป็น MCAR, MAR หรือ MNAR |
| การวิเคราะห์ | ข้อค้นพบนี้เป็นความสัมพันธ์หรือเหตุและผล มีตัวแปรแฝงอะไรได้บ้าง |
| แดชบอร์ด | ทำไมใช้ `st.cache_resource` กับ connection แต่ `st.cache_data` กับ query |
| Reproducibility | ถ้าเพื่อน clone repo วันนี้ ต้องทำกี่ขั้นจึงเห็นแดชบอร์ด |
| PDPA | ถ้าได้ข้อมูลผู้ป่วยรายคนจากโรงพยาบาล จะออกแบบระบบนี้ใหม่อย่างไร |
| AI | ยกตัวอย่างโค้ดที่ AI เขียนผิดและวิธีที่ตรวจพบ |

## 5. สถานะ repository ที่ต้องมี

ผู้สอนประเมิน repo ณ **tag `v1.0`** ที่ push ก่อนเวลานำเสนอ commit หลังจากนั้นไม่นำมาคิดคะแนน

```text
pm25-explorer/
├── README.md            ← คืออะไร · วิธีติดตั้ง · วิธีรัน · แหล่งข้อมูลและสัญญาอนุญาต · PDPA · ข้อจำกัด
├── questions.md         ← คำถาม + ข้อค้นพบสั้น ๆ ต่อคำถาม
├── AI_USAGE.md          ← บันทึกการใช้ AI ตลอดภาค + บทสะท้อนท้ายไฟล์
├── REFLECTION.md        ← บทสะท้อนตนเอง (แม่แบบในคู่มือปฏิบัติการ)
├── environment.yml      ← หรือ pyproject.toml + uv.lock
├── run_all.py           ← รัน pipeline ทั้งหมด
├── src/                 ← ดึง โหลด ทำความสะอาด ตรวจคุณภาพ (รันซ้ำได้)
├── notebooks/           ← การสำรวจสัปดาห์ที่ 2–13 (รัน Restart & Run All ผ่าน)
├── report/report.qmd    ← data story report
├── app/app.py           ← แดชบอร์ด drill-down 4 ระดับ
└── .gitignore           ← data/, *.duckdb, .env, outputs/, report/report.html
```

เงื่อนไขขั้นต่ำ (ถ้าไม่ครบ ผู้สอนอาจให้แก้และนำเสนอใหม่โดยหักคะแนน)

1. **ผ่าน fresh-clone test จากเพื่อน** (มี issue ผลการทดสอบที่ปิดแล้ว)
2. ไม่มีข้อมูล ความลับ (`.env`, API key) หรือข้อมูลส่วนบุคคลใน repo และในประวัติ commit
3. ทุก PR ของสัปดาห์ที่ 1–14 ถูก merge หรือปิดพร้อมเหตุผล `main` รันได้
4. README ระบุแหล่งข้อมูล สัญญาอนุญาต และวันที่ดึงข้อมูลชุดที่ใช้ในการนำเสนอ

## 7. ความซื่อสัตย์ทางวิชาการ

- การใช้ AI ช่วยเขียนโค้ดอนุญาตเสมอ แต่ต้องบันทึกใน `AI_USAGE.md` และอธิบายได้
- ถ้าใช้โค้ดหรือแนวคิดจากเพื่อน หรือแหล่งภายนอก ให้อ้างอิงใน README หรือ comment ในโค้ด
- การปกปิดว่าส่วนใดไม่ทำงาน แย่กว่าการบอกตรง ๆ ว่ายังไม่เสร็จพร้อมแผนแก้ไข การรายงานข้อจำกัดอย่างซื่อตรงได้คะแนนใน CLO4 และ CLO6

## สรุป

- นำเสนอ 10 นาที + ถามตอบ 5 นาที: ข้อค้นพบก่อน → demo end-to-end → คำตอบ → ข้อจำกัด → PDPA → การใช้ AI
- repo ถูกประเมิน ณ tag `v1.0` ต้องผ่าน fresh-clone test และไม่มีข้อมูล/ความลับ/ข้อมูลส่วนบุคคล
- เกณฑ์ 30 คะแนนครอบคลุม CLO1–CLO6 น้ำหนักมากที่สุดอยู่ที่การตอบคำถาม (CLO4) และการสื่อสาร (CLO5)
- ต้องอธิบายโค้ดของตนเองได้ทุกส่วน

## คำถามเตรียมตัว

1. ข้อค้นพบที่สำคัญที่สุดของโครงการคืออะไร เขียนให้ได้ใน 1 ประโยค
2. ถ้าต้องตัดเนื้อหาออกครึ่งหนึ่งเพื่อให้ทันเวลา จะเก็บส่วนใดไว้ เพราะอะไร
3. ข้อจำกัดใดที่ถ้าแก้ได้ จะเปลี่ยนคำตอบของคำถามมากที่สุด
4. ถ้าระบบนี้ถูกใช้โดยสำนักงานสาธารณสุขจังหวัด ต้องเปลี่ยนอะไรบ้างด้าน PDPA และความน่าเชื่อถือ
5. ส่วนใดของโค้ดที่ตนเองอธิบายได้ยากที่สุด ควรทบทวนก่อนวันนำเสนอ
