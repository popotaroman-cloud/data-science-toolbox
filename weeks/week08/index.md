## 1. Checkpoint นี้วัดอะไร

ครึ่งแรกของภาคการศึกษาเราสร้าง "ท่อส่งข้อมูล" ครึ่งหลังจะใช้ข้อมูลจากท่อนี้วาดกราฟ วิเคราะห์ และสร้างแดชบอร์ด ถ้าท่อรั่วหรือรันซ้ำไม่ได้ งานทุกสัปดาห์หลังจากนี้จะเสียตามไปด้วย Checkpoint 1 จึงตรวจ 3 เรื่อง

| เรื่อง | คำถามที่ผู้ประเมินถาม | CLO |
|---|---|---|
| **ทำงานได้** | รันทุกขั้นจนได้ `daily_pm25_clean` ต่อหน้าผู้ประเมินได้หรือไม่ | CLO2 |
| **ทำซ้ำได้** | คนอื่น clone repo แล้วรันตาม README ได้ผลเดียวกันหรือไม่ | CLO1 |
| **มีเหตุผล** | ทุกการตัดสินใจเรื่องคุณภาพข้อมูลอธิบายได้ มีหลักฐาน และรู้ผลกระทบต่อคำถามหรือไม่ | CLO3 |

> **ข้อควรจำ:** Checkpoint นี้ไม่ได้ให้คะแนนจำนวนกราฟหรือความสวยของสไลด์ pipeline ที่เรียบง่ายแต่ทำงานได้จริงและอธิบายได้ ดีกว่า pipeline ซับซ้อนที่รันไม่ผ่าน

## 2. Pipeline ที่ต้องทำงานครบ

```text
Air4Thai API ──► data/raw/*.json ──► data/pm25.duckdb ──► ตรวจคุณภาพ ──► measurements_clean
  (สัปดาห์ 3)                         stations, measurements  (สัปดาห์ 6)    daily_pm25_clean
                                      daily_pm25 (สัปดาห์ 4–5)               (สัปดาห์ 7)
```

| ขั้น | คำสั่ง | สิ่งที่ต้องได้ | ตรวจอย่างไร |
|---|---|---|---|
| 1. ดึงข้อมูล | `python src/fetch_air4thai.py` | ไฟล์ JSON ใหม่ใน `data/raw/` | มีไฟล์ชื่อมีวันเวลา ขนาดไม่เป็นศูนย์ |
| 2. โหลดเข้า DuckDB | `python src/load_duckdb.py` | ตาราง `stations`, `measurements` และ view `daily_pm25` | `SELECT count(*), max(ts) FROM measurements` |
| 3. ตรวจคุณภาพ | `python src/validate.py` | exit code 0 + ข้อความ `WARN` ที่อธิบายได้ | ลองใส่ข้อมูลเสียแล้วต้อง fail |
| 4. ทำความสะอาด | `python src/clean.py` | `measurements_clean`, `daily_pm25_clean` | `n_hours` อยู่ใน 0–24, ไม่มี key ซ้ำ |

แนะนำให้มี script รวมที่รันทุกขั้นตามลำดับและหยุดทันทีเมื่อขั้นใดล้มเหลว

`src/run_pipeline.py`

```python
"""รัน pipeline ทุกขั้นตามลำดับ หยุดทันทีถ้าขั้นใด error หรือ validate ไม่ผ่าน"""
import subprocess
import sys

STEPS = [
    "src/fetch_air4thai.py",
    "src/load_duckdb.py",
    "src/validate.py",
    "src/clean.py",
]

for step in STEPS:
    print(f"\n==> {step}")
    subprocess.run([sys.executable, step], check=True)   # check=True: exit code ไม่ใช่ 0 จะหยุด
print("\nPipeline เสร็จสมบูรณ์")
```

`sys.executable` ทำให้ทุกขั้นใช้ Python ตัวเดียวกับสภาพแวดล้อม `dstoolbox` ที่ activate อยู่

### ถ้า Air4Thai ล่มในวันนำเสนอ

API ภายนอกอาจล่มหรือเปลี่ยนรูปแบบได้ทุกเมื่อ ซึ่งไม่ใช่ความผิดของผู้เรียน แต่ *การไม่มีแผนสำรอง* เป็นความรับผิดชอบของผู้เรียน

1. เตรียมไฟล์ JSON ดิบที่ดึงไว้ล่วงหน้าหรือไฟล์ตัวอย่างจากผู้สอน (`data/sample/`) แล้วคัดลอกเข้า `data/raw/`
2. ข้ามขั้นที่ 1 แล้วรันขั้นที่ 2–4 จากไฟล์ดิบนั้น
3. เขียนวิธีนี้ไว้ใน README หัวข้อ "ถ้าดึงข้อมูลไม่ได้"

ผู้ประเมินจะไม่หักคะแนนถ้า API ล่มจริงและผู้เรียนสลับไปใช้แผนสำรองได้ภายใน 1 นาที

### README ที่เพื่อนทำตามได้

README ต้องเขียนสำหรับ **เพื่อนร่วมชั้นที่ไม่เคยเห็นโครงการนี้** และมีเพียงเครื่องที่ติดตั้ง Git กับ conda/uv ไว้แล้ว อย่างน้อยต้องมี

```markdown
## วิธีติดตั้ง
git clone https://github.com/<username>/pm25-explorer.git
cd pm25-explorer
conda env create -f environment.yml
conda activate dstoolbox

## วิธีรัน pipeline (รันจาก root ของ repo)
python src/run_pipeline.py
# หรือทีละขั้น: fetch_air4thai.py → load_duckdb.py → validate.py → clean.py

## ผลลัพธ์ที่ควรได้
data/pm25.duckdb ที่มี view daily_pm25_clean (ประมาณ ... แถว)

## ถ้าดึงข้อมูลไม่ได้
คัดลอกไฟล์ตัวอย่างจากผู้สอนไปไว้ที่ data/raw/ แล้วรันตั้งแต่ load_duckdb.py

## ข้อจำกัดที่ทราบ
...
```

ข้อผิดพลาดที่พบบ่อยคือ README ที่ "ถูกต้องบนเครื่องเจ้าของ" แต่ขาดขั้นตอนที่เจ้าของทำไปแล้วจนลืม เช่น สร้างโฟลเดอร์ `data/raw/` ด้วยมือ ติดตั้งแพ็กเกจเพิ่มโดยไม่ได้แก้ `environment.yml` หรือรันจากโฟลเดอร์ `src/` แทน root วิธีเดียวที่จับปัญหาเหล่านี้ได้คือ **fresh clone test** ในคู่มือปฏิบัติการ

## 4. รูปแบบการนำเสนอ

แต่ละคนมีเวลา **10 นาที: demo 7 นาที + ถาม-ตอบ 3 นาที** นำเสนอจากเครื่องของตนเอง โดยเริ่มจากสถานะที่ไม่มีฐานข้อมูล

| นาทีที่ | ส่วน | สิ่งที่ต้องแสดง |
|---|---|---|
| 0–1 | คำถามและแหล่งข้อมูล | คำถาม 1–2 ข้อจาก `questions.md` ที่ pipeline นี้รองรับ และแหล่งข้อมูล |
| 1–3 | Live demo | ลบ `data/pm25.duckdb` แล้วรัน `python src/run_pipeline.py` ระหว่างรอให้อธิบายแต่ละขั้น |
| 3–5 | คุณภาพข้อมูล | ปัญหาที่พบ 2–3 เรื่อง (เช่น sentinel, เซนเซอร์ค้าง) กฎที่เขียน และเหตุผลที่แบ่ง fail / warn |
| 5–7 | ข้อมูลสูญหาย | หลักฐานเรื่องกลไกการสูญหาย เกณฑ์ `n_hours` ที่เลือก และผล sensitivity analysis ต่อคำตอบ |
| 7–10 | ถาม-ตอบ | ผู้สอนและเพื่อนถาม อาจขอให้เปิดโค้ดบรรทัดใดก็ได้มาอธิบาย |

ถ้าใช้สไลด์ ให้มีไม่เกิน 4 หน้า ส่วนที่เหลือแสดงจาก terminal, notebook และไฟล์ใน repo โดยตรง

3. การตัดสินใจเรื่องข้อมูลสูญหายข้อใดที่มีผลต่อคำตอบใน `questions.md` มากที่สุด และคุณรายงานความไม่แน่นอนนั้นอย่างไร
4. มีอะไรในเครื่องของคุณที่ทำให้ pipeline ทำงานได้ แต่ไม่ได้อยู่ใน repo
