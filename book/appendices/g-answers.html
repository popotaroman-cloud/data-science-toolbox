1.1 สถิติศาสตร์บอกว่าสิ่งที่เห็นน่าเชื่อถือแค่ไหน การคำนวณทำให้การวิเคราะห์เป็นไปได้ ถูกต้อง และทำซ้ำได้ ความรู้เชิงโดเมนบอกว่าคำถามใดมีความหมายและผลแปลว่าอะไร ตัวอย่างความผิดพลาด: ขาดสถิติ เช่น สรุปว่าร้านค้าสาขาหนึ่งขายดีขึ้นจากยอดขายสองสัปดาห์ ทั้งที่ยอดขายรายสัปดาห์แกว่งมากตามปกติ · ขาดการคำนวณ เช่น รวมยอดจากหลายไฟล์ด้วยการคัดลอกวางแล้วลืมไฟล์หนึ่ง · ขาดความรู้เชิงโดเมน เช่น ตัดยอดขายที่สูงผิดปกติช่วงเทศกาลทิ้งเพราะคิดว่าเป็นข้อมูลผิด

1.2 นักสืบหาเบาะแสและสร้างข้อสันนิษฐาน แต่ไม่ได้ตัดสินว่าใครผิด ศาลเป็นผู้ชั่งน้ำหนักหลักฐานตามกระบวนการที่เข้มงวด ทั้งสองงานจำเป็นและเสริมกัน ผลของการสำรวจข้อมูลจึงเป็นข้อสันนิษฐานที่ต้องผ่านการวิเคราะห์เชิงยืนยันก่อนจะเป็นข้อสรุป และการวิเคราะห์เชิงยืนยันที่ไม่มีการสำรวจก่อนอาจทดสอบคำถามผิด

1.3 (1) วงจรของหนังสือเริ่มจากคำถามเชิงวิเคราะห์ ส่วน CRISP-DM เริ่มจากเป้าหมายขององค์กร (2) วงจรของหนังสือแยกขั้นจัดเก็บและขั้นตรวจคุณภาพออกมาเป็นขั้นที่มีผลงานชัดเจน และให้การสำรวจเป็นผลงานหลัก ขณะที่ CRISP-DM มองการสำรวจเป็นส่วนหนึ่งของ data understanding ก่อน modeling

1.4 สหสัมพันธ์วัดว่าจุดทั้งหมดอยู่ใกล้เส้นตรงเส้นเดียวแค่ไหน จุดผิดปกติที่อยู่ห่างจากเส้นมากทำให้ผลรวมของความเบี่ยงเบนกำลังสองจากเส้นเพิ่มขึ้นมาก ค่าสหสัมพันธ์จึงลดลงจากเกือบ 1 เหลือ 0.82 และยังดึงเส้นถดถอยให้ชันขึ้นด้วย ทั้งที่จุดอื่น 10 จุดเรียงเป็นเส้นตรงเกือบสมบูรณ์

1.5 การสำรวจต้องการความยืดหยุ่น ลองได้หลายแบบและทิ้งได้ง่าย notebook เหมาะกับงานนี้ ส่วนโค้ดทำความสะอาดข้อมูลต้องให้ผลเหมือนเดิมทุกครั้ง ผู้อื่นต้องตรวจสอบได้ และถูกเรียกใช้ซ้ำใน pipeline จึงควรเป็นไฟล์ .py ใน src/ ที่รันตามลำดับได้และไม่มีปัญหา hidden state

1.6 มัธยฐานของ \(y\) ไม่เท่ากันทุกชุด (ชุดที่ 1 = 7.58, ชุดที่ 2 = 8.14, ชุดที่ 3 = 7.11, ชุดที่ 4 = 7.04) แสดงว่าสถิติแบบทนทานอย่างมัธยฐานจับความต่างของรูปร่างข้อมูลได้บางส่วน เพราะไม่ถูกดึงด้วยค่าผิดปกติเหมือนค่าเฉลี่ย แต่มัธยฐานก็ยังเป็นตัวเลขเดียวที่บอกรูปร่างทั้งหมดไม่ได้ จึงยังต้องวาดกราฟ

1.7 ความคาดหวัง: ปี ค.ศ. 2022 มี 365 วัน แต่ละสถานีควรมี 8,760 แถว และค่า pm25 ไม่หายเกินร้อยละ 5 query ตัวอย่าง:

SELECT station_id, COUNT(*) AS n_rows, COUNT(pm25) AS n_pm25
FROM measurements
WHERE ts >= TIMESTAMP '2022-01-01' AND ts < TIMESTAMP '2023-01-01'
GROUP BY station_id
ORDER BY n_rows;

ถ้าผลไม่ตรงกับความคาดหวัง ให้แยกว่าแถวหาย (n_rows < 8,760) หรือค่าหาย (n_pm25 < n_rows) แล้วหาว่าส่วนที่ขาดอยู่ช่วงใด เช่น นับรายเดือน จากนั้นตั้งความคาดหวังใหม่ เช่น “สถานีที่เปิดกลางปีควรมีแถวเริ่มจากวันเปิด” แล้วตรวจต่อ

1.8 คำตอบขึ้นกับข้อมูลจริง คำตอบที่ดีต้องรายงานค่าเฉลี่ย มัธยฐาน ส่วนเบี่ยงเบนมาตรฐาน และสัดส่วนวันที่เกินมาตรฐานของทั้งสองสถานี และสรุปว่าถ้าส่วนเบี่ยงเบนมาตรฐานหรือสัดส่วนวันที่เกินมาตรฐานต่างกันชัดเจน สองสถานีไม่ได้ “เหมือนกัน” ในแง่การได้รับฝุ่นของประชาชน แม้ค่าเฉลี่ยใกล้กัน และควรระบุข้อจำกัดว่าเป็นการเลือกสถานีหลังดูข้อมูล

1.9 ตัวอย่าง: คำถาม “ปี ค.ศ. 2023 จังหวัดอุบลราชธานีมีวันที่ PM2.5 เกินมาตรฐานมากกว่าปี ค.ศ. 2022 หรือไม่” สิ่งที่ต้องสำรวจก่อน: (1) จำนวนสถานีในจังหวัดที่มีข้อมูลทั้งสองปี (2) สัดส่วนชั่วโมงที่มีข้อมูลในแต่ละเดือนของทั้งสองปี โดยเฉพาะช่วงฤดูฝุ่น (3) เกณฑ์ที่ใช้นับวันเกินมาตรฐานต้องเป็นเกณฑ์เดียวกันทั้งสองปี (4) ตัวชี้วัดอื่น เช่น ค่าสูงสุดรายวัน ให้ทิศทางเดียวกันหรือไม่

1.10 query ตัวอย่าง:

SELECT s.region, year(m.ts) AS year, COUNT(DISTINCT m.station_id) AS n_stations
FROM measurements AS m
JOIN stations AS s USING (station_id)
WHERE m.ts < TIMESTAMP '2024-01-01' AND m.pm25 IS NOT NULL
GROUP BY ALL
ORDER BY s.region, year;

       COUNT(*) FILTER (WHERE m.ts IS NOT NULL AND m.pm25 IS NULL)  AS n_null_value
FROM expected AS e
LEFT JOIN measurements AS m USING (station_id, ts)
GROUP BY e.station_id
ORDER BY e.station_id;

n_no_row คือข้อมูลสูญหายแบบ implicit (ไม่มีแถว) และ n_null_value คือแบบ explicit (มีแถวแต่ค่าว่าง) การนับเพียง COUNT(pm25) จากตาราง measurements มองเห็นเฉพาะแบบหลัง บทที่ 10 อธิบายความสำคัญของการแยกสองแบบนี้

8.5 fan-out คือการที่ key ฝั่งที่ควรไม่ซ้ำกลับซ้ำ ทำให้แถวหนึ่งจับคู่ได้หลายแถว จำนวนแถวหลัง join เพิ่มขึ้นและค่าสรุปผิด validate="many_to_one" ตรวจว่า key ฝั่งขวาไม่ซ้ำก่อน join ถ้าซ้ำจะแจ้ง MergeError และหยุดทันที

10.1 ตัวอย่าง: MCAR — ระบบรับส่งข้อมูลของหน่วยงานขัดข้องแบบสุ่มเป็นครั้งคราวโดยไม่สัมพันธ์กับเวลาหรือระดับฝุ่น · MAR — สถานีที่ตั้งในพื้นที่ห่างไกลมีไฟฟ้าดับบ่อยกว่าในฤดูฝนที่มีพายุ ซึ่งรู้ได้จากที่ตั้งและเดือน · MNAR — เครื่องวัดหยุดอัตโนมัติเมื่อค่าเกินช่วงที่วัดได้ ทำให้ค่าสูงสุดหายไปเสมอ

10.2 เพราะ isna() มองเห็นเฉพาะแถวที่มีอยู่แต่ค่าว่าง แถวของชั่วโมงที่ไม่ถูกบันทึกเลยไม่อยู่ในตารางให้นับ ต้องสร้างตารางเวลาเต็มของทุกสถานีกับทุกชั่วโมงที่ควรมี แล้ว reindex หรือ left join ข้อมูลจริงเข้าไป

10.3 สรุปได้ว่าการสูญหายสัมพันธ์กับระดับมลพิษ ข้อมูลจึงไม่น่าจะเป็น MCAR และการตัดค่าหายทิ้งอาจทำให้ค่าสรุปต่ำกว่าความจริง แต่ไม่ควรสรุปว่าพิสูจน์ได้ว่าเป็น MNAR เพราะอาจเป็น MAR ที่ขึ้นกับตัวแปรที่เห็น (เช่น ฤดูกาล) และไม่ควรสรุปว่าค่าที่หายสูงเท่ากับค่าของชั่วโมงก่อนหน้า

10.4 ช่องว่าง 6 ชั่วโมง: interpolate(limit=3) เติม 3 ชั่วโมงแรกด้วยเส้นตรงระหว่างค่าสองฝั่ง แล้วปล่อย 3 ชั่วโมงหลังว่าง ซึ่งทำให้ได้ค่าที่สร้างจากช่องว่างยาว ส่วน fill_short_gaps(max_gap=3) วัดความยาวช่องว่างได้ 6 ซึ่งเกิน 3 จึงไม่เติมเลยทั้ง 6 ชั่วโมง

10.5 ถ้าทุกชุดให้ค่าประมาณเท่ากัน \(B = 0\) และ \(T = W\) แปลว่าการเติมค่าไม่ได้เพิ่มความไม่แน่นอน ซึ่งเกิดได้เมื่อค่าที่หายไม่มีผลต่อค่าประมาณที่สนใจ หรือเมื่อการเติมค่าไม่ได้สุ่มจริง (เช่น ลืมตั้ง sample_posterior=True) ในกรณีหลัง ความแปรปรวนรวมจะต่ำเกินจริง

10.6 คำตอบขึ้นกับข้อมูล ให้คำนวณจากคอลัมน์ status หรือจากการเปรียบเทียบตารางเวลาเต็มกับตารางเดิม สัดส่วน implicit = จำนวนแถวที่ไม่มีในตารางเดิม / จำนวนแถวที่ควรมี สถานีที่มีสัดส่วน implicit สูงมักเป็นสถานีที่เปิดใหม่กลางช่วง (ควรตรวจวันเริ่มต้น) หรือมีช่วงหยุดทำงานยาวที่ระบบไม่ได้บันทึกแถวไว้

16.1 เลขประจำตัวประชาชน: ตัวระบุตรง · อายุ: ตัวระบุทางอ้อม · อำเภอ: ตัวระบุทางอ้อม · ผลตรวจสมรรถภาพปอด: ข้อมูลที่เป็นประเด็น และเป็นข้อมูลสุขภาพซึ่งเป็นข้อมูลอ่อนไหว · ค่าเฉลี่ย PM2.5 ของจังหวัด: ไม่ใช่ข้อมูลส่วนบุคคล (แต่เมื่อเชื่อมกับข้อมูลระดับบุคคลจะกลายเป็นคุณลักษณะของบุคคลนั้น) · วันที่เข้ารับบริการ: ตัวระบุทางอ้อม

16.2 การแฝงข้อมูลแทนตัวระบุด้วยรหัสที่ย้อนกลับได้ด้วยกุญแจหรือตารางจับคู่ จึงยังเป็นข้อมูลส่วนบุคคล การทำให้เป็นข้อมูลนิรนามทำให้ระบุตัวไม่ได้อีกด้วยวิธีที่สมเหตุสมผล ข้อมูลที่แทน HN ด้วย HMAC แต่ยังมีอายุ เพศ ตำบล และวันที่ เป็นข้อมูลที่แฝงแล้ว ไม่ใช่ข้อมูลนิรนาม ด้วยเหตุผลสองชั้น ชั้นแรก ผู้ถือกุญแจย้อนกลับได้ ชั้นที่สอง แม้ไม่มีกุญแจ ตัวระบุทางอ้อมสี่ตัวรวมกันยังระบุตัวได้ในชุมชนเล็ก

16.3 \(k = 3\) จาก equivalence class ที่เล็กที่สุด ถ้าต้องการ \(k \ge 5\) ทำได้สองทาง คือลดความละเอียดของตัวระบุทางอ้อมจนกลุ่มขนาด 3 รวมกับกลุ่มอื่น (เช่น รวมกลุ่มอายุหรือรวมอำเภอเป็นจังหวัด) หรือลบสามแถวนั้นออก ทางแรกรักษาแถวไว้แต่ลดความละเอียดทั้งชุด ทางที่สองรักษาความละเอียดแต่ทำให้ข้อมูลเอนเอียงถ้ากลุ่มที่ถูกลบมีลักษณะเฉพาะ ทั้งสองทางต้องบันทึกไว้

16.4 สเกล \(b = \Delta/\varepsilon = 1/0.1 = 10\) ส่วนเบี่ยงเบนมาตรฐาน \(\sqrt{2}\,b \approx 14.1\) ที่ \(\varepsilon = 1\) ได้ \(b = 1\) และส่วนเบี่ยงเบนมาตรฐานประมาณ 1.41 ค่า \(\varepsilon\) ที่เล็กกว่าสิบเท่าให้ความเป็นส่วนตัวสูงกว่าแต่สัญญาณรบกวนใหญ่กว่าสิบเท่า สำหรับช่องที่มีผู้ป่วยหลักร้อยยังใช้ได้ แต่ช่องที่มีหลักสิบจะแทบไม่มีความหมาย

16.5 SMOTE สร้างตัวอย่างใหม่จากตัวอย่างจริงและเพื่อนบ้าน ถ้าทำก่อนแบ่ง ตัวอย่างสังเคราะห์ในชุดทดสอบจะถูกสร้างจากตัวอย่างที่อยู่ในชุดฝึก (และกลับกัน) แบบจำลองจึงได้เห็นข้อมูลที่ใกล้กับชุดทดสอบมากระหว่างฝึก ผลบนชุดทดสอบจึงดีเกินจริงและไม่สะท้อนการใช้กับข้อมูลใหม่

16.6 ตัวอย่างแนวคำตอบ: คำถามระดับโรงเรียนหรืออำเภอต่อสัปดาห์ ควรขอจำนวนนักเรียนทั้งหมดและจำนวนที่ขาดเรียนด้วยเหตุป่วยต่อโรงเรียนต่อสัปดาห์ ไม่ขอชื่อ เลขประจำตัว วันเกิด หรือที่อยู่ของนักเรียน ถ้าต้องการแยกระดับชั้น ให้ขอเป็นช่วงชั้น และกำหนดให้ช่องที่มีน้อยกว่า 5 คนถูกระงับที่ฝั่งผู้ให้ข้อมูล ข้อมูลของเด็กต้องการความระมัดระวังเป็นพิเศษ และโครงการต้องผ่านคณะกรรมการจริยธรรม

16.7 นอกจากค่าว่าง ช่องว่างท้ายชื่อจังหวัด และแถวซ้ำ ให้เพิ่มเช่น วันที่นอกช่วงข้อมูล PM2.5 และรหัสโรคที่สะกดผิดรูปแบบ (เช่น j45 ตัวพิมพ์เล็ก) เก็บจำนวนที่ฉีดไว้ในตัวแปร แล้วเขียนการทดสอบ เช่น assert report["n_missing_age"] == 50 ที่รันกับผลของ src/validate.py การทดสอบที่ผ่านแปลว่า pipeline ตรวจพบปัญหาที่รู้ทั้งหมด

16.8 ใช้ query แบบ release ใน anonymization กับ pseudonymization กับข้อมูลปลอม แล้วคำนวณผลรวมของแต่ละจังหวัด × สัปดาห์ ถ้าทั้งผลรวมและช่องของกลุ่มอายุอื่นเผยแพร่ครบ ช่องที่ระงับไว้หนึ่งช่องคำนวณได้จาก ผลรวม ลบ ผลรวมของช่องที่เหลือ วิธีแก้คือระงับช่องที่สองในแถวเดียวกัน (ช่องที่เล็กที่สุดถัดไป) หรือเผยแพร่ผลรวมเป็นช่วง

16.9 ใช้โค้ดใน ข้อมูลสังเคราะห์: แบบกฎ (Faker), แบบสถิติ (copula), ★ แบบ deep learning (CTGAN) สร้างสองชุด แล้วเรียก utility_report(real, synthetic) และ utility_report(real, fake_daily) เทียบ ks_stat เปอร์เซ็นไทล์ที่ 95 ผลต่างสหสัมพันธ์สูงสุด และสัดส่วนวันเกินมาตรฐาน copula ที่เขียนเองใช้ควอนไทล์ของข้อมูลจริงแปลงกลับ จึงมักได้การแจกแจงขอบใกล้มาก แต่ไม่มีค่าเกินช่วงข้อมูลจริง ส่วน SDV อาจประมาณการแจกแจงขอบด้วยแบบจำลอง ทำให้หางต่างจากจริงได้ ทั้งสองแบบไม่รักษาความสัมพันธ์ตามเวลา (autocorrelation) เพราะสุ่มแต่ละแถวอย่างอิสระ

16.10 ใช้โค้ด DCR ใน การประเมินข้อมูลสังเคราะห์: utility กับ privacy แล้วเลือกห้าแถวจริงที่ pm25_mean สูงที่สุด คำนวณระยะจากแต่ละแถวถึงแถวสังเคราะห์ที่ใกล้ที่สุด (NearestNeighbors().fit(S).kneighbors(R[top5])) ถ้าระยะเหล่านี้ต่ำกว่าระยะระหว่างแถวจริงด้วยกันมาก แปลว่าข้อมูลสังเคราะห์สร้างค่าสุดขั้วของข้อมูลจริงขึ้นมาใหม่ ซึ่งในข้อมูลส่วนบุคคลจะเป็นความเสี่ยงสำคัญ copula ที่ใช้ควอนไทล์จริงมีแนวโน้มทำเช่นนี้กับหางของการแจกแจง

16.11 สร้าง features จาก daily_pm25_clean ของสถานีเดียวด้วย shift(1) สำหรับค่าเมื่อวาน และ y = (pm25_mean.shift(-1) > 37.5) แล้วตัดแถวสุดท้ายที่ไม่มีป้าย ประเมินสาม pipeline ด้วย TimeSeriesSplit(n_splits=5) และ average_precision สรุปโดยเทียบค่าเฉลี่ยและความแปรผันระหว่างรอบ ถ้า SMOTE ไม่ดีกว่า class_weight="balanced" อย่างชัดเจน ให้เลือกแบบที่ง่ายกว่า และเทียบกับ baseline ที่ทำนายว่า “พรุ่งนี้เหมือนวันนี้” ซึ่งมักแข็งแรงมากสำหรับข้อมูลที่มี autocorrelation สูง

20.4 st.cache_data พยายาม serialize ค่าที่คืนเพื่อเก็บและคืนสำเนา connection ของ DuckDB serialize ไม่ได้ จึงเกิด error และแม้ทำได้ การได้ connection สำเนาใหม่ทุกครั้งก็ไม่มีความหมาย st.cache_resource คืนออบเจกต์ตัวเดิมให้ทุก session ถ้าคืน DataFrame แล้วโค้ดส่วนใดแก้ DataFrame นั้น (เช่น เพิ่มคอลัมน์) การแก้จะกระทบทุก session และทุกการเรียกครั้งต่อไป ทำให้ตัวเลขผิดโดยหาสาเหตุยาก

20.5 ถ้าเพิ่มสถานีในพื้นที่ที่ฝุ่นน้อย ค่าเฉลี่ยของทุกสถานีจะลดลงแม้อากาศในพื้นที่เดิมไม่เปลี่ยน (Simpson’s paradox บทที่ 13) ตัวชี้วัดที่ทนกว่า: ค่าเฉลี่ยหรือสัดส่วนวันเกินมาตรฐานของ สถานีชุดเดียวกัน ที่มีข้อมูลทุกปี (balanced panel) หรือค่าที่ถ่วงน้ำหนักด้วยประชากรที่คงที่ และแสดงจำนวนสถานีคู่กับตัวชี้วัดเสมอ

20.6 สร้างฟังก์ชันใน src/queries.py ที่รับ con, where, params แล้วคืน DataFrame เช่น kpi(con, where, params), children(con, depth, where, params), monthly(con, where, params) ในแอปห่อด้วย @st.cache_data(ttl=600) โดยส่ง connection ผ่าน get_con().cursor() ภายในฟังก์ชันที่ cache ตรวจว่าตัวเลขเท่าเดิมด้วยการเปิดแอปฉบับเก่าและใหม่คู่กัน หรือดีกว่านั้น เขียนการทดสอบที่เทียบผลของ query เดิมกับฟังก์ชันใหม่

20.8 ใช้ query(..., db_mtime=db_version()) ทุกที่ และส่ง db_mtime เข้า get_con ด้วย (@st.cache_resource def get_con(db_mtime): ...) เพื่อให้เปิด connection ใหม่เมื่อไฟล์เปลี่ยน ขั้นทดลอง: หยุดแอป รัน python src/run_pipeline.py เปิดแอปใหม่ แล้วตรวจวันที่ของข้อมูลล่าสุดในส่วนบน ถ้าไม่ใส่ db_mtime แอปที่รีสตาร์ตก็จะเห็นข้อมูลใหม่อยู่แล้วเพราะ cache อยู่ในหน่วยความจำของกระบวนการ แต่ db_mtime จำเป็นเมื่อแอปทำงานต่อเนื่องและข้อมูลถูกเปลี่ยนโดยไม่รีสตาร์ต เช่น เมื่อใช้ไฟล์ฐานข้อมูลที่สร้างใหม่แล้วสลับชื่อไฟล์

20.9 ใช้โค้ดใน การออกแบบ drill-down หลายระดับ ทดสอบด้วยการ drill-down ถึงสถานี คัดลอก URL เปิดในแท็บใหม่ แล้วตรวจว่าแถบเส้นทางแสดงภาค จังหวัด และสถานีเดิม ต้องระวังกรณีที่ URL มีค่าที่ไม่มีในฐานข้อมูล ควรตรวจค่าที่อ่านจาก URL กับรายการที่มีจริงก่อนใช้

20.10 กรณีทดสอบที่ควรมี: (1) สัดส่วนวันเกินมาตรฐานของข้อมูลสามแถวใน ประสิทธิภาพ การทดสอบ และการ deploy ★ (2) เพิ่มแถวที่ is_complete เป็นเท็จและค่า 100 µg/m³ แล้วตรวจว่าผลไม่เปลี่ยน (3) ค่าเฉลี่ยระดับภาคถ่วงน้ำหนักด้วยสถานี-วัน คือ (30 + 50 + 40)/3 = 40 AppTest ที่ drill-down ครบ: เลือก pick_region, pick_province, pick_station ตามลำดับ ตรวจ not at.exception ทุกขั้น และตรวจว่า at.session_state["station"] ไม่เป็น None

20.11 ส่วนที่มักช้าที่สุดคือ query ที่อ่านข้อมูลรายวันทั้งหมดในระดับประเทศ และการวาดอนุกรมรายวันระดับสถานีที่มีหลายปี วิธีแก้ที่ได้ผล: ใช้ตารางสรุประดับสถานี × เดือนจากบทที่ 18 สำหรับแท่งและเส้นรายเดือน ตรวจว่า cache ทำงาน (การคลิกครั้งที่สองที่พารามิเตอร์เดิมควรเร็วมาก) และจำกัดอนุกรมรายวันตามช่วงวันที่ที่เลือก รายงานเป็นตารางเวลาของแต่ละส่วนก่อนและหลัง

บทที่ 21

21.1 ตัวอย่างสำหรับอุบลราชธานี: คำถาม “ในฤดูแล้ง (ม.ค.–เม.ย.) ค่าเฉลี่ยรายวันของสถานีในจังหวัดอุบลราชธานีสูงกว่าฤดูฝน (มิ.ย.–ก.ย.) กี่เท่า และจำนวนวันเกินมาตรฐานต่อปีเปลี่ยนไปอย่างไร” · ตัวชี้วัด: อัตราส่วนค่าเฉลี่ยเรขาคณิตแล้งต่อฝน และจำนวนสถานี-วันที่เกิน 37.5 µg/m³ ต่อปี · ข้อมูล: daily_pm25_clean ของสถานีในจังหวัด · ผู้ใช้: สำนักงานสิ่งแวดล้อมภาคและสำนักงานสาธารณสุขจังหวัด · บทหลัก: 13 (อัตราส่วนและช่วงความเชื่อมั่น), 14 (ฤดูกาล), 18 (การรวมระดับจังหวัด)

21.2 ตัวอย่าง: (1) ถ้าใช้ PostgreSQL แทน DuckDB ระบบจะรองรับหลายผู้เขียนพร้อมกันและการเข้าถึงผ่านเครือข่าย แต่ต้องติดตั้งและดูแล server การส่งต่อโครงการและ fresh-clone test ยากขึ้นมาก (2) ถ้าแปลงข้อมูลทันทีแล้วทิ้ง JSON ดิบ เมื่อพบว่าการแปลงค่าแทนผิด จะแก้ข้อมูลย้อนหลังไม่ได้ เพราะ Air4Thai ให้เพียงค่าล่าสุดผ่าน endpoint ที่ใช้ ข้อมูลที่ดึงไว้แล้วจะเสียถาวร

21.3 ต้องรัน load_duckdb.py ใหม่ (ซึ่งเติม stations.region จาก CSV) ตารางที่ได้รับผลคือ stations โดยตรง และทุกตารางหรือ view ที่ใช้ region ซึ่งในระบบนี้คำนวณตอน query จึงเปลี่ยนตามทันทีเมื่อ stations เปลี่ยน station_clusters ไม่ได้ใช้ภาคในการจัดกลุ่มจึงไม่ต้องสร้างใหม่ แต่ crosstab กับภาคในรายงานต้อง render ใหม่ และแดชบอร์ดต้องล้าง cache หรือรีสตาร์ต ถ้า daily_outlier_flags ใช้สถานีในจังหวัดเดียวกันเป็นหลักฐาน และจังหวัดก็ผิดด้วย ต้องสร้างตารางธงใหม่

21.4 แนวคำตอบ: key ซ้ำ เวลาผิด และลำดับชั้นผิดควรเป็น fail เพราะทำให้ทุกตัวเลขผิดโดยไม่มีทางรู้ ค่าติดลบหลังแปลงค่าแทนควรเป็น fail เพราะบอกว่ากฎการแปลงพลาด PM2.5 มากกว่า PM10 เซนเซอร์ค้าง สถานีที่ไม่ส่งข้อมูล และพิกัดไม่ตรงจังหวัดควรเป็น warn เพราะเกิดได้จริงกับข้อมูลที่ถูกต้องส่วนใหญ่ และการหยุด pipeline ทุกครั้งที่สถานีหนึ่งขัดข้องจะทำให้ระบบใช้งานไม่ได้ ข้อโต้แย้งที่สมเหตุสมผลคือ ถ้าสัดส่วนของชั่วโมงที่ PM2.5 มากกว่า PM10 สูงผิดปกติทั้งเครือข่าย ควรเป็น fail เพราะอาจหมายถึงการสลับคอลัมน์ในขั้นโหลด

21.5 เห็นจากกราฟ: “กราฟของปี 2563–2566 ชี้ว่าภาค … มีสัดส่วนวันเกินมาตรฐานสูงกว่าภาคอื่น” · ทดสอบในช่วงสำรวจ: “ในฤดูแล้งปี 2563–2566 สถานีภาค … มีมัธยฐาน PM2.5 สูงกว่าสถานีกรุงเทพมหานครประมาณ … เท่า (95% CI … ถึง …; p ที่ปรับแล้ว = …)” · ยืนยันด้วยข้อมูลช่วงยืนยัน: เพิ่ม “และพบผลทิศทางเดียวกันในปี 2567–2568 ซึ่งไม่ได้ใช้ในการตั้งสมมติฐาน (อัตราส่วน … เท่า)”

21.6 ย้ายโค้ดจาก outlier คือความผิดพลาดหรือเหตุการณ์จริง และกรณีศึกษาของบทที่ 15 เป็นฟังก์ชัน build_clusters(con) และ build_outlier_flags(con) ในไฟล์ใหม่ ซึ่งเปิดฐานข้อมูลแบบเขียนได้ครั้งเดียวแล้วสร้างทั้งสองตารางด้วย CREATE OR REPLACE TABLE เพิ่มชื่อไฟล์ใน STEPS ของ src/run_pipeline.py ทดสอบด้วยการลบ data/pm25.duckdb แล้วรัน python src/run_pipeline.py (หรือใช้ไฟล์ตัวอย่าง) จากนั้นตรวจด้วย SELECT count(*) FROM station_clusters และ SELECT count(*) FROM daily_outlier_flags

21.7 ใช้โค้ดของบทที่ 13 (ฟังก์ชัน station_units, compare, bootstrap และ multipletests) และบทที่ 18 (roll_up สำหรับสัดส่วนวันเกินมาตรฐาน) ตามลำดับใน ตารางที่ 21.7 ข้อสรุปต้องมีครบเจ็ดองค์ประกอบ คือ ขนาดของผลพร้อมหน่วย ช่วงความเชื่อมั่น ช่วงเวลาและประชากร วิธี p-value จำนวนหน่วย และข้อจำกัด

21.8 วนรายการสถานีของภาค สำหรับแต่ละสถานีเตรียมอนุกรมรายเดือนตาม การแยกองค์ประกอบ: classical decomposition และ STL ข้ามสถานีที่ยังมีช่องว่างกลางอนุกรมหลังเติม (บันทึกจำนวนที่ข้าม) แล้วเก็บ f_s, f_t, เดือนที่ res.seasonal สูงสุด และอัตราส่วนเดือนสูงสุดต่อต่ำสุด สรุปด้วยมัธยฐานของภาค และรายงานสถานีที่มีเดือนยอดต่างจากสถานีส่วนใหญ่

21.9 ใช้ exceedance_by_threshold ในกรณีศึกษาของบทที่ 21 แล้วเทียบคอลัมน์ rank_12 กับ rank_18 และขนาดการเปลี่ยนของ share_over_std ระหว่างเกณฑ์ เลือกรูปแบบใน ตารางที่ 21.14 ที่ตรงกับผล ถ้าภาคใดได้รับผลมากกว่าภาคอื่น ให้ตรวจ missing_by_month ใน คุณภาพข้อมูลและข้อมูลสูญหาย ของภาคนั้นประกอบ เพื่อดูว่าการสูญหายกระจุกในเดือนที่ฝุ่นหนักหรือไม่

21.10 ตารางที่ดีมีข้อค้นพบที่อ่านเข้าใจได้โดยไม่ต้องดูกราฟ และระดับความมั่นใจที่บอกเหตุผลสั้น ๆ ถ้าเพื่อนเล่ากลับมาผิดหรือไม่ครบ ให้แก้ประโยคข้อค้นพบ ไม่ใช่เพิ่มคำอธิบาย ประโยคที่ต้องอธิบายเพิ่มมักยาวเกินหรือรวมหลายประเด็นในประโยคเดียว

บทที่ 22

22.1 ตัวอย่าง: (1) เกณฑ์ความครบถ้วนรายวัน เกี่ยวกับหลักประโยชน์และไม่ก่ออันตราย เพราะถ้าการสูญหายเป็น MNAR การตัดวันที่ไม่ครบทำให้ประเมินปัญหาต่ำไป ผู้ใช้อาจเชื่อว่าปลอดภัยกว่าความจริง (2) การจัดอันดับจังหวัดในแดชบอร์ด เกี่ยวกับหลักประโยชน์และไม่ก่ออันตรายและความยุติธรรม เพราะอาจตีตราพื้นที่ที่ความต่างอยู่ในช่วงความไม่แน่นอน (3) การเชื่อมกับข้อมูลผู้ป่วย เกี่ยวกับหลักการเคารพบุคคลและการเคารพกฎหมาย (PDPA)

def test_exceed_days_counts_station_days_and_completeness():
    def hours(sid, n, value):
        return pd.DataFrame({"station_id": sid, "pm25": value,
                             "ts": pd.date_range("2025-01-01", periods=n, freq="h")})
    hourly = pd.concat([hours("a", 24, 50.0),     # ครบและเกิน → นับ
                        hours("b", 24, 10.0),     # ครบแต่ไม่เกิน → ไม่นับ
                        hours("c", 2, 80.0)])     # เกินแต่วัดได้ 2 ชั่วโมง → ไม่นับ
    assert exceed_days(hourly) == 1

def exceed_days(hourly, min_hours=18, std=37.5):
    h = hourly.assign(date=hourly["ts"].dt.floor("D"))
    d = h.groupby(["station_id", "date"]).agg(mean=("pm25", "mean"), n=("pm25", "count"))
    return int(((d["n"] >= min_hours) & (d["mean"] > std)).sum())
