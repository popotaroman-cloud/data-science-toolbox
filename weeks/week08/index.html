สัปดาห์ที่ 8: Checkpoint 1 นำเสนอ data pipeline

CLO: CLO1–CLO3 · น้ำหนักคะแนน: 20% · เครื่องมือ: ทุกเครื่องมือจากสัปดาห์ที่ 1–7 (ไม่มีเครื่องมือใหม่) ผลงานที่เพิ่มในระบบ: pipeline ที่ทำงานครบตั้งแต่ดึงข้อมูลถึงชุดข้อมูลรายวันที่สะอาด + repo ที่เพื่อน clone แล้วรันตามได้ + tag checkpoint1

วัตถุประสงค์การเรียนรู้

เมื่อจบสัปดาห์นี้ ผู้เรียนสามารถ

  1. สาธิต data pipeline ของตนเองที่ทำงานครบทุกขั้นจากเครื่องที่สะอาดได้ (CLO1, CLO2)
  2. เขียนคำแนะนำการติดตั้งและรันที่ผู้อื่นทำตามได้โดยไม่ต้องถามเจ้าของ repo (CLO1)
  3. อธิบายและให้เหตุผลการตัดสินใจเรื่องคุณภาพข้อมูลและข้อมูลสูญหาย พร้อมผลที่อาจทำให้คำตอบเอนเอียง (CLO3)
  4. ตอบคำถามเกี่ยวกับโค้ดของตนเอง รวมถึงส่วนที่ใช้ AI ช่วยเขียนได้ (CLO1, CLO6)

1. Checkpoint นี้วัดอะไร

ครึ่งแรกของภาคการศึกษาเราสร้าง “ท่อส่งข้อมูล” ครึ่งหลังจะใช้ข้อมูลจากท่อนี้วาดกราฟ วิเคราะห์ และสร้างแดชบอร์ด ถ้าท่อรั่วหรือรันซ้ำไม่ได้ งานทุกสัปดาห์หลังจากนี้จะเสียตามไปด้วย Checkpoint 1 จึงตรวจ 3 เรื่อง

เรื่อง คำถามที่ผู้ประเมินถาม CLO
ทำงานได้ รันทุกขั้นจนได้ daily_pm25_clean ต่อหน้าผู้ประเมินได้หรือไม่ CLO2
ทำซ้ำได้ คนอื่น clone repo แล้วรันตาม README ได้ผลเดียวกันหรือไม่ CLO1
มีเหตุผล ทุกการตัดสินใจเรื่องคุณภาพข้อมูลอธิบายได้ มีหลักฐาน และรู้ผลกระทบต่อคำถามหรือไม่ CLO3

ข้อควรจำ: Checkpoint นี้ไม่ได้ให้คะแนนจำนวนกราฟหรือความสวยของสไลด์ pipeline ที่เรียบง่ายแต่ทำงานได้จริงและอธิบายได้ ดีกว่า pipeline ซับซ้อนที่รันไม่ผ่าน

2. Pipeline ที่ต้องทำงานครบ

Air4Thai API ──► data/raw/*.json ──► data/pm25.duckdb ──► ตรวจคุณภาพ ──► measurements_clean
  (สัปดาห์ 3)                         stations, measurements  (สัปดาห์ 6)    daily_pm25_clean
                                      daily_pm25 (สัปดาห์ 4–5)               (สัปดาห์ 7)
ขั้น คำสั่ง สิ่งที่ต้องได้ ตรวจอย่างไร
1. ดึงข้อมูล python src/fetch_air4thai.py ไฟล์ JSON ใหม่ใน data/raw/ มีไฟล์ชื่อมีวันเวลา ขนาดไม่เป็นศูนย์
2. โหลดเข้า DuckDB python src/load_duckdb.py ตาราง stations, measurements และ view daily_pm25 SELECT count(*), max(ts) FROM measurements
3. ตรวจคุณภาพ python src/validate.py exit code 0 + ข้อความ WARN ที่อธิบายได้ ลองใส่ข้อมูลเสียแล้วต้อง fail
4. ทำความสะอาด python src/clean.py measurements_clean, daily_pm25_clean n_hours อยู่ใน 0–24, ไม่มี key ซ้ำ

แนะนำให้มี script รวมที่รันทุกขั้นตามลำดับและหยุดทันทีเมื่อขั้นใดล้มเหลว

src/run_pipeline.py

"""รัน pipeline ทุกขั้นตามลำดับ หยุดทันทีถ้าขั้นใด error หรือ validate ไม่ผ่าน"""
import subprocess
import sys

STEPS = [
    "src/fetch_air4thai.py",
    "src/load_duckdb.py",
    "src/validate.py",
    "src/clean.py",
]

for step in STEPS:
    print(f"\n==> {step}")
    subprocess.run([sys.executable, step], check=True)   # check=True: exit code ไม่ใช่ 0 จะหยุด
print("\nPipeline เสร็จสมบูรณ์")

sys.executable ทำให้ทุกขั้นใช้ Python ตัวเดียวกับสภาพแวดล้อม dstoolbox ที่ activate อยู่

ถ้า Air4Thai ล่มในวันนำเสนอ

API ภายนอกอาจล่มหรือเปลี่ยนรูปแบบได้ทุกเมื่อ ซึ่งไม่ใช่ความผิดของผู้เรียน แต่ การไม่มีแผนสำรอง เป็นความรับผิดชอบของผู้เรียน

  1. เตรียมไฟล์ JSON ดิบที่ดึงไว้ล่วงหน้าหรือไฟล์ตัวอย่างจากผู้สอน (data/sample/) แล้วคัดลอกเข้า data/raw/
  2. ข้ามขั้นที่ 1 แล้วรันขั้นที่ 2–4 จากไฟล์ดิบนั้น
  3. เขียนวิธีนี้ไว้ใน README หัวข้อ “ถ้าดึงข้อมูลไม่ได้”

ผู้ประเมินจะไม่หักคะแนนถ้า API ล่มจริงและผู้เรียนสลับไปใช้แผนสำรองได้ภายใน 1 นาที

README ที่เพื่อนทำตามได้

README ต้องเขียนสำหรับ เพื่อนร่วมชั้นที่ไม่เคยเห็นโครงการนี้ และมีเพียงเครื่องที่ติดตั้ง Git กับ conda/uv ไว้แล้ว อย่างน้อยต้องมี

cd pm25-explorer
conda env create -f environment.yml

# หรือทีละขั้น: fetch_air4thai.py → load_duckdb.py → validate.py → clean.py

## ถ้าดึงข้อมูลไม่ได้
คัดลอกไฟล์ตัวอย่างจากผู้สอนไปไว้ที่ data/raw/ แล้วรันตั้งแต่ load_duckdb.py

## ข้อจำกัดที่ทราบ
...

ข้อผิดพลาดที่พบบ่อยคือ README ที่ “ถูกต้องบนเครื่องเจ้าของ” แต่ขาดขั้นตอนที่เจ้าของทำไปแล้วจนลืม เช่น สร้างโฟลเดอร์ data/raw/ ด้วยมือ ติดตั้งแพ็กเกจเพิ่มโดยไม่ได้แก้ environment.yml หรือรันจากโฟลเดอร์ src/ แทน root วิธีเดียวที่จับปัญหาเหล่านี้ได้คือ fresh clone test ในคู่มือปฏิบัติการ

4. รูปแบบการนำเสนอ

แต่ละคนมีเวลา 10 นาที: demo 7 นาที + ถาม-ตอบ 3 นาที นำเสนอจากเครื่องของตนเอง โดยเริ่มจากสถานะที่ไม่มีฐานข้อมูล

นาทีที่ ส่วน สิ่งที่ต้องแสดง
0–1 คำถามและแหล่งข้อมูล คำถาม 1–2 ข้อจาก questions.md ที่ pipeline นี้รองรับ และแหล่งข้อมูล
1–3 Live demo ลบ data/pm25.duckdb แล้วรัน python src/run_pipeline.py ระหว่างรอให้อธิบายแต่ละขั้น
3–5 คุณภาพข้อมูล ปัญหาที่พบ 2–3 เรื่อง (เช่น sentinel, เซนเซอร์ค้าง) กฎที่เขียน และเหตุผลที่แบ่ง fail / warn
5–7 ข้อมูลสูญหาย หลักฐานเรื่องกลไกการสูญหาย เกณฑ์ n_hours ที่เลือก และผล sensitivity analysis ต่อคำตอบ
7–10 ถาม-ตอบ ผู้สอนและเพื่อนถาม อาจขอให้เปิดโค้ดบรรทัดใดก็ได้มาอธิบาย

ถ้าใช้สไลด์ ให้มีไม่เกิน 4 หน้า ส่วนที่เหลือแสดงจาก terminal, notebook และไฟล์ใน repo โดยตรง

5. เกณฑ์การให้คะแนน (20 คะแนน)

เกณฑ์ คะแนน ดีมาก (เต็ม) พอใช้ (ประมาณครึ่ง) ต้องปรับปรุง (0–1)
1. Pipeline ทำงานได้ 6 ทุกขั้นรันต่อหน้าผู้ประเมินโดยไม่ต้องแก้โค้ดสด ได้ daily_pm25_clean ที่ถูกต้อง มีแผนสำรองเมื่อ API ล่ม ทำงานครบแต่ต้องแก้เล็กน้อยระหว่าง demo หรือต้องรันบางขั้นด้วยมือใน notebook ขาดขั้นใดขั้นหนึ่ง หรือรันไม่ผ่าน
2. Reproducibility 4 เพื่อนผ่าน fresh clone test ตาม README โดยไม่ต้องถาม environment.yml ครบ ไม่มี path แบบตายตัว รันซ้ำได้ผลเดิม เพื่อนรันได้แต่ต้องถามหรือแก้ 1–2 จุด เพื่อนรันตาม README ไม่ได้
3. เหตุผลด้านคุณภาพข้อมูล 5 กฎ pandera ครอบคลุมและทดสอบแล้ว แบ่ง fail / warn มีเหตุผล วิเคราะห์กลไกการสูญหายด้วยหลักฐาน มี sensitivity analysis และ data_dictionary.md บันทึกทุกการตัดสินใจพร้อมผลที่อาจเอนเอียง มีกฎและการจัดการค่าว่าง แต่เหตุผลหรือหลักฐานไม่ครบ หรือไม่โยงกับคำถาม ใช้ dropna() หรือ fillna() โดยไม่มีเหตุผล หรือไม่มีกฎตรวจ
4. Code และ Git practice 3 โค้ดหลักอยู่ใน src/ เป็น .py ที่รันซ้ำได้ ทุกสัปดาห์มี PR ที่ review แล้ว commit message สื่อความหมาย ไม่มีข้อมูลหรือความลับใน repo AI_USAGE.md เป็นปัจจุบัน โครงสร้างพอใช้ แต่ commit ใหญ่รวบครั้งเดียว หรือ PR บางสัปดาห์ไม่มี review โค้ดอยู่ใน notebook เท่านั้น หรือ commit ข้อมูล/ความลับ
5. การนำเสนอและตอบคำถาม 2 ตรงเวลา ลำดับชัด ตอบคำถามเรื่องโค้ดของตนเองได้ทุกข้อ รวมถึงส่วนที่ใช้ AI ช่วย เกินเวลาเล็กน้อย หรือตอบบางคำถามไม่ได้ อธิบายโค้ดของตนเองไม่ได้
รวม 20

ตามนโยบาย AI ของรายวิชา: ถ้าผู้เรียนอธิบายส่วนใดของโค้ดที่ส่งไม่ได้ ผู้ประเมินอาจไม่ให้คะแนนเกณฑ์ที่เกี่ยวข้องกับส่วนนั้น

คะแนน fresh clone test (เกณฑ์ 2) มาจากแบบบันทึกของเพื่อนที่ทำการทดสอบในคาบปฏิบัติการ ส่วนการ review ของผู้เรียนให้เพื่อนนับรวมในคะแนน peer review 10% ของรายวิชา

6. คำถามที่ผู้ประเมินมักถาม

เตรียมคำตอบสั้น ๆ สำหรับคำถามแนวนี้

หมวด ตัวอย่างคำถาม
Pipeline ถ้ารัน load_duckdb.py สองครั้งติดกัน จะได้ข้อมูลซ้ำหรือไม่ ทำไม
Pipeline ถ้า Air4Thai เปลี่ยนชื่อ field ใน JSON โค้ดส่วนไหนจะพัง และจะรู้ได้อย่างไร
คุณภาพข้อมูล ทำไมขอบบนของ pm25 จึงเป็นค่านี้
คุณภาพข้อมูล กฎข้อใดเคยจับข้อผิดพลาดจริงได้
ข้อมูลสูญหาย ข้อมูลของคุณน่าจะเป็น MCAR, MAR หรือ MNAR หลักฐานคืออะไร
ข้อมูลสูญหาย ถ้าเปลี่ยนเกณฑ์จาก 18 เป็น 24 ชั่วโมง คำตอบของคำถามข้อ 1 เปลี่ยนอย่างไร
Reproducibility ถ้าเพื่อนใช้ macOS หรือ Windows คนละแบบกับคุณ อะไรอาจพัง
AI ส่วนไหนที่ใช้ AI ช่วย และตรวจสอบผลอย่างไร

7. เชื่อมกับครึ่งหลังของภาคการศึกษา

ตั้งแต่สัปดาห์ที่ 9 ทุกกราฟและการวิเคราะห์จะอ่านจาก daily_pm25_clean และ measurements_clean ผลป้อนกลับจาก Checkpoint นี้ (เช่น กฎที่ขาด หรือเกณฑ์ที่ควรทบทวน) ให้เปิดเป็น GitHub Issue ใน repo ของตนเอง แล้วแก้ใน PR ภายในสัปดาห์ที่ 9 การแก้ pipeline หลังจากนี้ทำได้เสมอ แต่ต้องอัปเดต data_dictionary.md ทุกครั้ง

สรุป

  • Checkpoint 1 (20%) ตรวจว่า pipeline ทำงานได้ ทำซ้ำได้ และมีเหตุผลด้านคุณภาพข้อมูล
  • pipeline ต้องรันได้ครบ 4 ขั้น: fetch → DuckDB → validate → clean และควรมี run_pipeline.py ที่หยุดเมื่อขั้นใดล้มเหลว
  • README ต้องเขียนให้เพื่อนที่ไม่รู้จักโครงการทำตามได้ และพิสูจน์ด้วย fresh clone test
  • นำเสนอ 7 นาที + ถาม-ตอบ 3 นาที เน้น live demo และเหตุผล ไม่ใช่สไลด์
  • เตรียมแผนสำรองเมื่อ API ล่ม และสร้าง tag checkpoint1 ก่อนกำหนด

คำถามทบทวน (ตรวจความพร้อมด้วยตนเอง)

  1. ถ้าลบโฟลเดอร์ data/ ทั้งหมดตอนนี้ ต้องใช้กี่คำสั่งจึงได้ daily_pm25_clean กลับมา และมีขั้นใดที่ต้องทำด้วยมือหรือไม่
  2. ถ้าข้อมูลมีแถวซ้ำเล็ดลอดเข้ามา pipeline ของคุณจะหยุดที่ขั้นใด
  3. การตัดสินใจเรื่องข้อมูลสูญหายข้อใดที่มีผลต่อคำตอบใน questions.md มากที่สุด และคุณรายงานความไม่แน่นอนนั้นอย่างไร
  4. มีอะไรในเครื่องของคุณที่ทำให้ pipeline ทำงานได้ แต่ไม่ได้อยู่ใน repo
