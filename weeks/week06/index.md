## 1. ทำไมต้องตรวจคุณภาพข้อมูลก่อนวิเคราะห์

ในสัปดาห์ที่ 3–5 เราได้ pipeline ที่ดึงข้อมูลจาก Air4Thai (`src/fetch_air4thai.py`) โหลดเข้า `data/pm25.duckdb` (`src/load_duckdb.py`) และสร้าง view `daily_pm25` แล้ว แต่ "โหลดเข้าได้" ไม่ได้แปลว่า "เชื่อถือได้"

ลองนึกถึงคำถามใน `questions.md` เช่น *"ในเดือนมีนาคม จังหวัดเชียงใหม่มีกี่วันที่ค่าเฉลี่ย 24 ชั่วโมงของ PM2.5 เกินมาตรฐาน 37.5 µg/m³"* คำตอบจะผิดทันทีถ้า

- สถานีส่งค่า `-1` แทน "ไม่มีข้อมูล" แล้วเรานำไปเฉลี่ยรวม ค่าเฉลี่ยจะต่ำกว่าความจริง
- เซนเซอร์ค้างที่ค่าเดิม 30 ชั่วโมงติดกัน วันนั้นดูเหมือน "อากาศดีสม่ำเสมอ"
- เวลาถูกเลื่อนไป 7 ชั่วโมงเพราะแปลง timezone ผิด ค่ารายวันจะรวมชั่วโมงข้ามวันกัน

> **หลักการ:** ตรวจคุณภาพข้อมูล *ก่อน* ตอบคำถาม และเขียนกฎตรวจเป็นโค้ด เพื่อให้ตรวจซ้ำได้ทุกครั้งที่ดึงข้อมูลใหม่

## 2. มิติของคุณภาพข้อมูล (Data quality dimensions)

| มิติ | ความหมาย | ตัวอย่างใน PM2.5 | ตรวจอย่างไร |
|---|---|---|---|
| **Completeness** (ความครบถ้วน) | ข้อมูลที่ควรมีนั้นมีครบหรือไม่ | สถานีหนึ่งมีข้อมูลเพียง 14 จาก 24 ชั่วโมง | นับค่า NULL และนับแถวต่อสถานีต่อวัน (`n_hours`) |
| **Validity** (ความถูกต้องตามรูปแบบ) | ค่าอยู่ในชนิดและช่วงที่เป็นไปได้ | `pm25 = -1`, `pm25 = 999`, `station_id` ที่ไม่มีในตาราง `stations` | กฎชนิดข้อมูล ช่วงค่า และรายการค่าที่อนุญาต |
| **Consistency** (ความสอดคล้อง) | ข้อมูลไม่ขัดแย้งกันเอง | `pm25 > pm10` เป็นเวลานาน (PM2.5 เป็นส่วนหนึ่งของ PM10) | เปรียบเทียบคอลัมน์ที่สัมพันธ์กัน |
| **Uniqueness** (ความไม่ซ้ำ) | หนึ่งเหตุการณ์มีหนึ่งแถว | `(station_id, ts)` ซ้ำเพราะรัน load สองครั้ง | ตรวจ key ซ้ำ |
| **Timeliness** (ความทันเวลา) | ข้อมูลใหม่พอสำหรับการใช้งาน | ข้อมูลล่าสุดในฐานข้อมูลเก่ากว่า 3 วัน | เทียบ `max(ts)` กับเวลาปัจจุบัน |
| **Accuracy** (ความแม่นยำ) | ค่าตรงกับความจริง | เซนเซอร์ค้าง หรือ calibration ผิด | ตรวจด้วยโค้ดได้ยากที่สุด ต้องเทียบกับสถานีใกล้เคียงหรือแหล่งอื่น |

มิติ 5 ข้อแรกตรวจด้วยกฎได้ค่อนข้างตรงไปตรงมา แต่ **accuracy** มักต้องใช้หลักฐานจากภายนอกและการตีความของผู้วิเคราะห์ ข้อมูลที่ผ่านกฎทุกข้อจึงยังอาจไม่แม่นยำก็ได้

## 3. ปัญหาเฉพาะของข้อมูล Air4Thai

ข้อมูลจากเซนเซอร์ภาคสนามมีปัญหาที่ profiling ทั่วไปมองไม่เห็น ต้องรู้จักโดเมนจึงจะตั้งคำถามถูก โค้ดในหัวข้อนี้สมมติว่าโหลดตาราง `measurements` มาเป็น DataFrame `m` แล้ว

```python
import duckdb

con = duckdb.connect("data/pm25.duckdb", read_only=True)
m = con.execute("SELECT * FROM measurements ORDER BY station_id, ts").df()
m.shape   # เช่น (150000, 8)
```

### 3.1 Sentinel value: ตัวเลขที่แปลว่า "ไม่มีข้อมูล"

ระบบหลายแห่งใช้ตัวเลขพิเศษแทนค่าว่าง เช่น `-1`, `-99`, `999` หรือ `9999` ถ้าไม่แปลงเป็น NULL ตอนโหลด ตัวเลขเหล่านี้จะปนเข้าไปในค่าเฉลี่ย **ค่าที่ Air4Thai ใช้จริงอาจเปลี่ยนไปตามเวลา ให้ตรวจจากข้อมูลจริงของตนเอง** อย่าเชื่อเอกสารนี้

```python
# ค่าที่ซ้ำบ่อยผิดปกติ มักเป็น sentinel
m["pm25"].value_counts().head(10)

# ค่าติดลบ และค่าที่สูงผิดธรรมชาติ
m.loc[(m["pm25"] < 0) | (m["pm25"] >= 999), ["station_id", "ts", "pm25"]]
```

ถ้าพบ sentinel ให้แก้ที่ **ขั้นโหลด** (`src/load_duckdb.py`) โดยแปลงเป็น NULL ส่วนกฎในสัปดาห์นี้ทำหน้าที่เป็น *ด่านตรวจ* ที่จับได้หากมีค่าเล็ดลอดเข้ามา

### 3.2 เซนเซอร์ค้าง (stuck sensor / flat line)

เซนเซอร์ที่เสียบางครั้งส่งค่าเดิมซ้ำต่อเนื่องหลายชั่วโมง ค่านั้นอยู่ในช่วงปกติ จึงผ่านกฎช่วงค่า แต่ในธรรมชาติ PM2.5 แทบไม่เคยคงที่พอดีหลายชั่วโมง

```python
# ค่าเบี่ยงเบนมาตรฐานในหน้าต่าง 6 ชั่วโมงเป็นศูนย์ = ค่าเดิม 6 ชั่วโมงติด
m["roll_std"] = (
    m.groupby("station_id")["pm25"]
     .transform(lambda s: s.rolling(6).std())
)
stuck = m[m["roll_std"] == 0]
stuck.groupby("station_id").size().sort_values(ascending=False).head()
```

หน้าต่าง 6 ชั่วโมงเป็นค่าที่เลือกเอง ผู้เรียนต้องให้เหตุผลและบันทึกไว้ เพราะถ้าหน้าต่างสั้นเกินจะได้ false positive ในช่วงที่อากาศนิ่งจริง

### 3.3 เวลาคลาดเคลื่อน (timezone shift)

ตารางของเราเก็บ `ts` เป็นเวลา Asia/Bangkok (UTC+7) ถ้าขั้นใดขั้นหนึ่งตีความเวลาเป็น UTC ข้อมูลจะเลื่อนไป 7 ชั่วโมง สัญญาณที่ควรตรวจ

| สัญญาณ | วิธีดู |
|---|---|
| รูปแบบรายชั่วโมงแปลก | ค่าเฉลี่ย PM2.5 ตามชั่วโมงของวัน โดยทั่วไปมักสูงช่วงเช้าตรู่และค่ำ ถ้ายอดไปอยู่ผิดช่วงอย่างชัดเจน ให้สงสัย |
| ข้อมูลจากอนาคต | `ts` มากกว่าเวลาปัจจุบัน |
| key ซ้ำเป็นช่วง | รันดึงข้อมูลซ้ำแล้วเวลาถูกแปลงคนละแบบ ทำให้ช่วงเดียวกันปรากฏสองครั้ง |

```python
m.groupby(m["ts"].dt.hour)["pm25"].mean().round(1)   # รูปแบบตามชั่วโมง 0–23
```

รูปแบบรายชั่วโมงไม่ใช่การพิสูจน์ แต่เป็นเบาะแสให้กลับไปตรวจโค้ดแปลงเวลาในสัปดาห์ที่ 3–4

## 4. Data profiling อัตโนมัติ

**Data profiling** คือการสรุปข้อมูลทุกคอลัมน์อย่างเป็นระบบ เช่น ชนิดข้อมูล จำนวนค่าว่าง การกระจาย ค่าซ้ำ และความสัมพันธ์ระหว่างคอลัมน์ เครื่องมือ profiling ทำสิ่งเหล่านี้ให้ในคำสั่งเดียว

| เครื่องมือ | ประเภท | ผลลัพธ์ | เหมาะกับ |
|---|---|---|---|
| **ydata-profiling** | หลัก | รายงาน HTML ครบทุกคอลัมน์ พร้อมคำเตือน (alerts) | สำรวจชุดข้อมูลใหม่ครั้งแรก |
| skimpy | เสริม | ตารางสรุปใน terminal / notebook | ดูภาพรวมเร็ว ๆ ไม่ต้องเปิดไฟล์ |
| Sweetviz | เสริม | รายงาน HTML เน้นเปรียบเทียบสองชุดข้อมูล | เทียบก่อน/หลังทำความสะอาด (ต้อง `pip install sweetviz` เอง) |

### ydata-profiling

```python
from ydata_profiling import ProfileReport

profile = ProfileReport(
    m.drop(columns=["roll_std"]),
    title="Air4Thai measurements — profiling",
    minimal=True,          # ปิดส่วนที่คำนวณหนัก เหมาะกับข้อมูลหลายแสนแถว
)
profile.to_file("reports/profile_measurements.html")
```

ส่วนที่ควรอ่านในรายงาน: **Alerts** (เช่น คอลัมน์มีค่าว่างมาก ค่าศูนย์มาก ค่าคงที่) · **Variables** (ช่วงค่าและ histogram ของ `pm25`) · **Missing values** · **Duplicate rows**

### skimpy และ Sweetviz (เสริม)

```python
from skimpy import skim
skim(m)                                    # สรุปทุกคอลัมน์ในหน้าเดียว

import sweetviz as sv                      # เสริม: pip install sweetviz
sv.analyze(m).show_html("reports/sweetviz.html", open_browser=False)
```

### ทำไมไม่ commit รายงาน HTML

รายงาน profiling ฝังข้อมูลและรูปภาพไว้ในไฟล์ ขนาดมักอยู่ที่หลาย MB และ *สร้างใหม่ได้เสมอ* จากโค้ด จึงจัดเป็น output เหมือน `data/`

| ไฟล์ | commit หรือไม่ | เหตุผล |
|---|---|---|
| `reports/*.html` | ไม่ (ใส่ใน `.gitignore`) | ใหญ่ สร้างใหม่ได้ และอาจมีตัวอย่างข้อมูลดิบอยู่ข้างใน |
| `reports/profiling_notes.md` | commit | การตีความของผู้เรียน ซึ่งสร้างใหม่ด้วยโค้ดไม่ได้ |
| โค้ดที่สร้างรายงาน (notebook / script) | commit | ทำให้คนอื่นสร้างรายงานเดิมได้ |

ถ้าต้องการแนบรายงานให้ผู้สอนดู ให้ใช้ `minimal=True` และแนบใน PR หรือระบบส่งงาน ไม่ใช่ commit เข้า repo

## 5. Profiling อัตโนมัติไม่ได้แทนการตีความ

รายงาน profiling บอกว่า *อะไร* ผิดปกติในเชิงสถิติ แต่ไม่บอกว่า *ทำไม* และ *สำคัญต่อคำถามของเราหรือไม่*

| รายงานบอกว่า | สิ่งที่ผู้วิเคราะห์ต้องถามต่อ |
|---|---|
| `pm25` มีค่าว่าง 8% | ว่างกระจายทั่วไป หรือกระจุกที่บางสถานี/บางช่วงเวลา (สัปดาห์ที่ 7) |
| `pm25` skewed ขวามาก | เป็นธรรมชาติของมลพิษช่วงหมอกควัน หรือเป็นค่าผิดพลาด |
| `pm25` กับ `pm10` correlation สูง | คาดได้อยู่แล้ว ไม่ใช่ข้อค้นพบใหม่ |
| ไม่มี alert เรื่องค่าคงที่ | รายงานดูทั้งคอลัมน์ จึงไม่เห็นเซนเซอร์ค้างเป็นช่วงในสถานีเดียว |
| ไม่มี alert ใด ๆ | ไม่ได้แปลว่าข้อมูลดี เช่น timezone shift ไม่มีทางเห็นจาก histogram |

> **ข้อควรจำ:** profiling เป็นจุดเริ่มต้นของการตั้งคำถาม ทุก alert ที่สำคัญต้องมีบันทึกใน `profiling_notes.md` ว่าตรวจต่ออย่างไรและตัดสินใจอย่างไร

## 6. เขียนกฎตรวจข้อมูลเป็นโค้ดด้วย pandera

การตรวจด้วยตาใน notebook ทำครั้งเดียวแล้วจบ แต่ pipeline ดึงข้อมูลใหม่ทุกวัน เราจึงเขียน **schema** ที่ระบุว่าข้อมูลที่ดีหน้าตาเป็นอย่างไร แล้วให้ pandera ตรวจให้ทุกครั้ง

`src/schema.py`

```python
"""กฎตรวจคุณภาพของตาราง measurements (สัปดาห์ที่ 6)"""
import duckdb
import pandera.pandas as pa   # pandera รุ่นเก่ากว่า 0.24 ใช้ import pandera as pa

DB_PATH = "data/pm25.duckdb"
PM25_MAX = 1000          # µg/m³ ขอบบนที่ "เป็นไปไม่ได้" ทางกายภาพ ไม่ใช่ค่าสูงที่หายาก
SENTINELS = [-1, 999, 9999]

def allowed_station_ids(db_path: str = DB_PATH) -> list[str]:
    con = duckdb.connect(db_path, read_only=True)
    ids = [row[0] for row in con.execute("SELECT station_id FROM stations").fetchall()]
    con.close()
    return ids

def measurements_schema(station_ids: list[str]) -> pa.DataFrameSchema:
    pollutant = lambda upper: pa.Column(
        float, [pa.Check.ge(0), pa.Check.le(upper)], nullable=True
    )
    return pa.DataFrameSchema(
        columns={
            "station_id": pa.Column(str, pa.Check.isin(station_ids)),
            "ts": pa.Column("datetime64[ns]"),
            "pm25": pa.Column(
                float,
                [pa.Check.ge(0), pa.Check.le(PM25_MAX), pa.Check.notin(SENTINELS)],
                nullable=True,
            ),
            "pm10": pollutant(2000),
            "o3": pollutant(1000),
            "co": pollutant(100),
            "no2": pollutant(1000),
            "so2": pollutant(1000),
        },
        unique=["station_id", "ts"],   # หนึ่งสถานี หนึ่งชั่วโมง หนึ่งแถว
        coerce=True,                   # แปลงชนิดข้อมูลก่อนตรวจ
        strict=False,                  # ยอมให้มีคอลัมน์อื่นเพิ่มได้
    )
```

ขอบบนของสารอื่นนอกจาก PM2.5 ในตัวอย่างเป็นค่าตั้งต้นแบบหลวม ๆ ผู้เรียนต้องตรวจหน่วยของแต่ละสารจากข้อมูลจริง (เช่น CO มักรายงานเป็น ppm ส่วน O3 เป็น ppb) แล้วปรับให้สมเหตุสมผล

กฎแต่ละข้อจับมิติคุณภาพใด

| กฎ | มิติ |
|---|---|
| ชนิดข้อมูล `float`, `datetime64[ns]` | validity |
| `pm25 >= 0`, `<= 1000`, ไม่เป็น sentinel | validity |
| `station_id` อยู่ในตาราง `stations` | validity / consistency |
| `unique=["station_id", "ts"]` | uniqueness |
| `nullable=True` | ตั้งใจยอมให้มีค่าว่าง แล้วไปจัดการในสัปดาห์ที่ 7 |

### ใช้ schema ใน pipeline

```python
import pandera.pandas as pa
from schema import allowed_station_ids, measurements_schema

schema = measurements_schema(allowed_station_ids())
try:
    schema.validate(m, lazy=True)     # lazy=True: รวบรวมข้อผิดพลาดทั้งหมดก่อนรายงาน
    print("ผ่านทุกกฎ")
except pa.errors.SchemaErrors as err:
    print(err.failure_cases.head(20)) # DataFrame ของแถว/ค่าที่ไม่ผ่าน
```

## 7. Fail หรือ warn: ปัญหาไหนควรหยุด pipeline

ถ้าทุกปัญหาทำให้ pipeline หยุด ระบบจะใช้งานไม่ได้เลยเพราะข้อมูลจริงไม่เคยสมบูรณ์ แต่ถ้าแค่เตือนทุกเรื่อง ข้อมูลเสียจะไหลไปถึงแดชบอร์ด หลักในการแบ่งคือ

- **Fail (หยุด):** ปัญหาที่ทำให้ผลวิเคราะห์ผิดแน่นอน หรือบอกว่าโค้ดของเราเองมี bug เช่น key ซ้ำ, sentinel เล็ดลอด, `station_id` ที่ไม่รู้จัก, ชนิดข้อมูลผิด
- **Warn (เตือนและบันทึก):** ปัญหาที่คาดได้จากธรรมชาติของข้อมูล ต้องรู้แต่ไม่ต้องหยุด เช่น สัดส่วนค่าว่างสูงขึ้น, เซนเซอร์ค้าง, ค่าสูงมากแต่ยังเป็นไปได้, ข้อมูลล่าสุดเก่ากว่า 2 วัน

| ตรวจอะไร | Fail / Warn | เหตุผล |
|---|---|---|
| `(station_id, ts)` ซ้ำ | Fail | ค่าเฉลี่ยรายวันถ่วงน้ำหนักผิด และบอกว่า load มี bug |
| `pm25 < 0` หรือเป็น sentinel | Fail | ต้องแก้ที่ขั้นโหลด |
| `pm25 > 500` | Warn | เกิดได้จริงช่วงไฟป่าภาคเหนือ แต่ควรมีคนดู |
| เซนเซอร์ค้าง ≥ 6 ชั่วโมง | Warn | ส่งต่อให้สัปดาห์ที่ 7 ตัดสินใจ |
| `max(ts)` เก่ากว่า 2 วัน | Warn | API อาจล่มชั่วคราว |

ใน `src/validate.py` กฎ fail ใช้ pandera แล้วจบด้วย `sys.exit(1)` เพื่อให้คำสั่งถัดไปใน pipeline ไม่ทำงาน ส่วนกฎ warn เขียนเป็นฟังก์ชัน pandas ธรรมดาที่พิมพ์ข้อความ `WARN` และทำงานต่อ (pandera มีพารามิเตอร์ `raise_warning=True` ใน `pa.Check` สำหรับกรณีนี้เช่นกัน แต่ฟังก์ชันธรรมดาอ่านง่ายกว่าสำหรับผู้เริ่มต้น)

## 8. เชื่อมกับสัปดาห์ถัดไป

กฎในสัปดาห์นี้ตั้งใจ *ยอมให้มีค่าว่าง* (`nullable=True`) เพราะการตัดสินใจว่าจะทิ้ง เติม หรือเก็บค่าว่างไว้ ต้องดูก่อนว่า **ทำไม** ข้อมูลจึงหาย ซึ่งเป็นเรื่องของสัปดาห์ที่ 7 และผลการตรวจทั้งหมดจะเป็นส่วนหนึ่งของ Checkpoint 1 ในสัปดาห์ที่ 8

## สรุป

- คุณภาพข้อมูลมี 6 มิติ: completeness, validity, consistency, uniqueness, timeliness, accuracy
- ข้อมูลเซนเซอร์ Air4Thai มีปัญหาเฉพาะ: sentinel value, เซนเซอร์ค้าง, timezone shift ซึ่งต้องรู้โดเมนจึงจะหาเจอ
- ydata-profiling ช่วยให้เห็นภาพรวมเร็ว แต่ผู้วิเคราะห์ต้องตีความและบันทึกการตัดสินใจเอง
- รายงาน HTML ไม่ commit ส่วนบันทึกการตีความและโค้ดต้อง commit
- pandera เปลี่ยนความคาดหวังต่อข้อมูลให้เป็นโค้ดที่ตรวจซ้ำได้ และต้องแยกกฎ fail กับ warn อย่างมีเหตุผล

## คำถามทบทวน

1. ข้อมูลที่ผ่าน schema ทุกข้อ ยังอาจผิดได้อย่างไร ยกตัวอย่างจากมิติ accuracy
2. เพราะเหตุใดเซนเซอร์ค้างจึงผ่านกฎช่วงค่า และต้องตรวจด้วยวิธีใด
3. ถ้าตั้งขอบบนของ `pm25` ไว้ที่ 200 µg/m³ จะเกิดปัญหาอะไรกับข้อมูลช่วงหมอกควันภาคเหนือ
4. ทำไม key ซ้ำควรเป็น fail แต่ค่าว่างสูงขึ้นควรเป็นแค่ warn
5. รายงาน profiling ของเพื่อนไม่มี alert ใดเลย เพื่อนสรุปว่า "ข้อมูลสะอาดแล้ว" ผู้เรียนจะโต้แย้งอย่างไร
