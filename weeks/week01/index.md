## 1. Exploratory Data Analysis คืออะไร

**EDA** คือกระบวนการทำความรู้จักข้อมูลก่อนสรุปผลหรือสร้างโมเดล John Tukey ผู้บัญญัติคำนี้ (1977) เปรียบ EDA เป็น *งานนักสืบ* คือหาเบาะแส ส่วนการทดสอบสมมติฐานเชิงยืนยัน (confirmatory analysis) เปรียบเป็น *งานศาล* ที่ตัดสินว่าเบาะแสนั้นเชื่อถือได้หรือไม่

EDA ตอบคำถามประมาณนี้

- ข้อมูลมีอะไรบ้าง ครอบคลุมช่วงเวลาและพื้นที่ไหน
- ข้อมูลมีคุณภาพพอจะตอบคำถามของเราหรือไม่ (ค่าหาย ค่าผิดปกติ หน่วยไม่ตรงกัน)
- ตัวแปรมีการกระจายแบบไหน และสัมพันธ์กันอย่างไร
- มีรูปแบบอะไรที่น่าสนใจและควรตรวจสอบต่อ

> **ข้อควรจำ:** EDA *สร้าง* สมมติฐาน แต่ไม่ได้ *พิสูจน์* สมมติฐาน (รายละเอียดในสัปดาห์ที่ 2)

### Data lifecycle

```text
ตั้งคำถาม → ได้มาซึ่งข้อมูล → จัดเก็บ → ทำความสะอาด/แปลงรูป → สำรวจ (EDA) → สื่อสารผล
    ↑                                                                    │
    └─────────────────── คำถามใหม่จากสิ่งที่พบ ←──────────────────────────┘
```

วงจรนี้วนซ้ำเสมอ สิ่งที่พบระหว่างสำรวจมักนำไปสู่คำถามใหม่ หรือทำให้ต้องกลับไปเก็บข้อมูลเพิ่ม

## 2. ระบบที่จะสร้างตลอดภาคการศึกษา

ผู้เรียนแต่ละคนสร้าง **ระบบสำรวจข้อมูลหนึ่งระบบใน repository เดียว** และต่อยอดทุกสัปดาห์

```text
แหล่งข้อมูล (API / เว็บ)  →  DuckDB (ไฟล์เดียว)  →  pandas  →  Plotly  →  Streamlit dashboard
   สัปดาห์ 3                 สัปดาห์ 4             สัปดาห์ 5–7   สัปดาห์ 9–13   สัปดาห์ 14
```

| สัปดาห์ | สิ่งที่เพิ่มเข้าไปในระบบ |
|---|---|
| 1 | สภาพแวดล้อม + repo |
| 2 | คำถามเชิงวิเคราะห์ (`questions.md`) |
| 3–5 | pipeline ดึง จัดเก็บ และแปลงข้อมูล |
| 6–7 | กฎตรวจคุณภาพข้อมูลและชุดข้อมูลสะอาด |
| 8 | **Checkpoint 1:** pipeline ทำงานครบ |
| 9–13 | กราฟและการวิเคราะห์ที่ตอบคำถาม |
| 14–15 | รายงานและแดชบอร์ด |

**โจทย์ตัวอย่าง:** ระบบสำรวจคุณภาพอากาศ PM2.5 ของประเทศไทยจาก Air4Thai (กรมควบคุมมลพิษ) ผู้เรียนเลือกโดเมนอื่นได้ เช่น ข้อมูลน้ำฝน อุบัติเหตุทางถนน หรือราคาสินค้าเกษตร แต่ต้องมีลักษณะครบ 3 ข้อ

1. ดึงข้อมูลจากแหล่งจริงได้ด้วยโค้ด ไม่ใช่ดาวน์โหลดไฟล์ด้วยมือครั้งเดียว
2. มีมิติเวลา และควรมีมิติพื้นที่ด้วย
3. ข้อมูลไม่สะอาดสมบูรณ์ เพื่อให้ได้ฝึกตรวจคุณภาพข้อมูล

## 3. สภาพแวดล้อมการทำงาน (Environment)

### ทำไมต้องจัดการสภาพแวดล้อม

"รันได้บนเครื่องผม" ไม่ใช่ผลงานที่ทำซ้ำได้ โค้ดเดียวกันอาจให้ผลต่างกัน ถ้าเวอร์ชันของ pandas หรือ Python ต่างกัน **สภาพแวดล้อม (environment)** คือชุดของ Python และไลบรารีที่แยกเป็นของแต่ละโครงการ และบันทึกเป็นไฟล์ให้คนอื่นสร้างตามได้

| เครื่องมือ | ไฟล์ที่บันทึกสภาพแวดล้อม | จุดเด่น |
|---|---|---|
| **conda** (Miniconda / Miniforge) | `environment.yml` | ติดตั้งไลบรารีที่มีส่วนประกอบภาษา C ได้ง่าย เช่น GeoPandas |
| **uv** | `pyproject.toml` + `uv.lock` | เร็วมาก lock เวอร์ชันได้แม่นยำ |

รายวิชานี้รองรับทั้งสองแบบ ไฟล์ทั้งสองอยู่ที่ root ของ repo รายวิชา

```bash
# conda
conda env create -f environment.yml
conda activate dstoolbox

# uv
uv sync
uv run jupyter lab
```

### VS Code, Jupyter และ terminal

| เครื่องมือ | ใช้ทำอะไร |
|---|---|
| **terminal** | รันคำสั่ง ติดตั้งแพ็กเกจ ใช้ Git รัน script |
| **Jupyter** (`.ipynb`) | สำรวจข้อมูลแบบโต้ตอบ เห็นผลทันทีทีละ cell |
| **VS Code** | แก้ไข `.py` / `.md` / `.ipynb` ในที่เดียว มี terminal และ Git ในตัว |

**หลักการแบ่งงาน:** ใช้ notebook สำหรับ *สำรวจ* ส่วนโค้ดที่ต้องรันซ้ำ เช่น ดึงข้อมูลหรือโหลดเข้าฐานข้อมูล ให้ย้ายไปเป็นไฟล์ `.py` เพราะ notebook รันข้ามลำดับ cell ได้ และมักทำให้ผลทำซ้ำไม่ได้

คำสั่ง terminal ที่ต้องใช้คล่อง

| คำสั่ง | ความหมาย |
|---|---|
| `pwd` / `cd <dir>` / `ls` | ดูตำแหน่งปัจจุบัน / เปลี่ยนโฟลเดอร์ / แสดงไฟล์ |
| `mkdir <dir>` | สร้างโฟลเดอร์ |
| `python script.py` | รัน script |
| `conda activate <env>` / `uv run <cmd>` | ใช้สภาพแวดล้อมของโครงการ |

## 4. Version control ด้วย Git และ GitHub

### แนวคิดหลัก

**Git** บันทึก "ภาพถ่าย" ของโครงการทุกครั้งที่เราสั่ง commit ทำให้ย้อนกลับไปดูได้ว่าเปลี่ยนอะไร เมื่อไร และเพราะอะไร **GitHub** เป็นที่เก็บ repository บนอินเทอร์เน็ต และเป็นเครื่องมือทำงานร่วมกันผ่าน pull request

| คำศัพท์ | ความหมาย |
|---|---|
| repository (repo) | โฟลเดอร์โครงการที่ Git ติดตามการเปลี่ยนแปลง |
| commit | การบันทึกการเปลี่ยนแปลงหนึ่งครั้ง พร้อมข้อความอธิบาย |
| branch | สายการพัฒนาแยก ใช้ลองของใหม่โดยไม่กระทบ `main` |
| remote / push / pull | repo ปลายทางบน GitHub / ส่งขึ้น / ดึงลงมา |
| pull request (PR) | คำขอรวม branch เข้า `main` พร้อมพื้นที่ให้เพื่อน review |

### วงจรการทำงานพื้นฐาน

```bash
git switch -c week01-setup        # สร้าง branch ใหม่
# ... แก้ไขไฟล์ ...
git status                        # ดูว่าไฟล์ใดเปลี่ยน
git add README.md                 # เลือกไฟล์ที่จะ commit
git commit -m "เพิ่มคำอธิบายโครงการ"
git push -u origin week01-setup   # ส่งขึ้น GitHub แล้วเปิด pull request
```

### สิ่งที่ห้าม commit

| ห้าม commit | เหตุผล | ทำอย่างไรแทน |
|---|---|---|
| ไฟล์ข้อมูลขนาดใหญ่ (`data/`, `*.duckdb`) | repo บวม และข้อมูลอาจมีลิขสิทธิ์ | commit *โค้ดที่ดึงข้อมูล* แทนตัวข้อมูล |
| รหัสผ่าน / API key (`.env`) | หลุดสู่สาธารณะทันทีที่ push และลบออกจากประวัติได้ยาก | เก็บใน `.env` แล้วใส่ใน `.gitignore` |
| ข้อมูลส่วนบุคคล | ผิด PDPA | ใช้ข้อมูลสังเคราะห์ (สัปดาห์ที่ 12) |

### commit message ที่ดี

ข้อความ commit ควรบอกว่า *ทำอะไรและเพราะอะไร* เพราะคนที่อ่านอาจเป็นเพื่อนร่วมทีมหรือตัวเราเองในอีก 3 เดือน

- ❌ `update`, `แก้`, `final2`
- ✅ `เพิ่ม script ดึงข้อมูล PM2.5 รายชั่วโมงจาก Air4Thai`
- ✅ `แก้หน่วยเวลาเป็น Asia/Bangkok ก่อนบันทึกลง DuckDB`

commit history ของผู้เรียนเป็นส่วนหนึ่งของคะแนนแบบฝึกปฏิบัติรายสัปดาห์ จึงควร commit บ่อย ๆ เป็นชิ้นเล็กที่มีความหมาย

## 5. โครงสร้าง repository ของโครงการผู้เรียน

```text
pm25-explorer/
├── README.md            ← โครงการนี้คืออะไร รันอย่างไร
├── questions.md         ← คำถามเชิงวิเคราะห์ (สัปดาห์ที่ 2)
├── AI_USAGE.md          ← บันทึกการใช้ AI
├── environment.yml      ← หรือ pyproject.toml
├── .gitignore
├── src/                 ← โค้ดที่รันซ้ำได้ (ดึงข้อมูล โหลดเข้า DuckDB)
├── notebooks/           ← การสำรวจข้อมูล
├── app/                 ← Streamlit dashboard (สัปดาห์ที่ 14)
└── data/                ← ไม่ commit (อยู่ใน .gitignore)
```

## 6. การใช้ AI ในรายวิชา

อนุญาตให้ใช้ LLM ช่วยเขียนโค้ดได้ โดยผู้เรียนต้อง

1. อธิบายโค้ดที่ส่งได้ทุกบรรทัด
2. บันทึกการใช้ AI ใน `AI_USAGE.md`
3. ตรวจผลลัพธ์จาก AI กับข้อมูลจริงเสมอ AI มักสร้างชื่อคอลัมน์ ชื่อฟังก์ชัน หรือ endpoint ของ API ที่ไม่มีอยู่จริงขึ้นมาเอง

## สรุป

- EDA คือการทำความรู้จักข้อมูลเพื่อหาเบาะแสและสร้างสมมติฐาน
- ทั้งเทอมจะสร้างระบบเดียว: แหล่งข้อมูล → DuckDB → pandas → Plotly → Streamlit
- สภาพแวดล้อมต้องบันทึกเป็นไฟล์ เพื่อให้ผู้อื่นทำซ้ำได้
- Git บันทึกประวัติ GitHub ใช้ทำงานร่วมกัน และห้าม commit ข้อมูล ความลับ หรือข้อมูลส่วนบุคคล

## คำถามทบทวน

1. EDA ต่างจาก confirmatory analysis อย่างไร ยกตัวอย่างจากข้อมูล PM2.5
2. ทำไมโค้ดดึงข้อมูลจึงควรเป็นไฟล์ `.py` มากกว่าอยู่ใน notebook
3. ถ้าเผลอ commit ไฟล์ `.env` ที่มี API key แล้ว push ขึ้น GitHub ควรทำอะไรเป็นอันดับแรก
4. `environment.yml` ช่วยให้งานทำซ้ำได้อย่างไร และยังมีอะไรที่ไฟล์นี้ไม่ได้รับประกัน
